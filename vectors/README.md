# Golden vectors

Each `*.json` file here is a list of input/output cases that the Rust crate, the Python bindings and the WebAssembly bindings must all reproduce. The format is `golden-vectors@1` from [evidence-kernel](https://github.com/chethandvg/evidence-kernel).

| File | Checks |
|---|---|
| `records.json` | `rhythms()` and `get(id)` return the records of `data/rhythms.json` unchanged. |
| `frequency.json` | `frequency_hz(id)` for every record: periods, frequencies and rates in hertz; everything else rejected. |
| `heart_rate.json` | `heart_rate_at(weeks)`: exact at each weekly median, placed at the middle of its week (6.5 to 10.5 weeks), linear in between, rejected outside 6.5 to 10.5 weeks. |
| `cell_count.json` | `cell_count_at(hours)`: the step function over t2 to t8, rejected outside 0 to t8. |

The vectors are generated by [`generate.py`](generate.py), the reference (oracle) implementation. It reads the measurements from `data/rhythms.yaml`, not from the generated JSON the crate embeds, and computes every helper result exactly with rational arithmetic before rounding once to a double. Regenerate with:

```bash
python vectors/generate.py
```

**Tolerances.** `frequency.json` and `heart_rate.json` allow a relative error of 1e-15; `records.json` and `cell_count.json` must match exactly. Each Rust helper rounds at most three times in double precision (a period in hours is 1 / (60 · (60 · T)); an interpolated heart rate is b0 + (x − w0) · (b1 − b0) / (w1 − w0), where the subtractions and the division by one week are exact), so it is within about 3u of the exact value, with u = 2⁻⁵³ ≈ 1.1e-16. The oracle rounds once, so the two differ by at most about 4u ≈ 4.4e-16, below 1e-15. Cell counts are integers found by comparing doubles, with no arithmetic, so they cannot differ.
